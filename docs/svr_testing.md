# SVR implementation checks and validation record

## Purpose and scope

Notebook 5 compares a scaled RBF SVR with persistence and ordinary least-squares regression on the same prepared observations. It fits on training data, uses validation data to select among 12 settings and never loads the reserved final-test CSV.

The notebook is an application of the Week 5.3 SVR workflow, not a new implementation of the numerical SVR solver. Scikit-learn provides the solver. The project code constructs, checks and evaluates that workflow.

This document separates three kinds of evidence:

1. **Implementation tests:** synthetic cases check that the source code and intended use of library functions behave as specified.
2. **Notebook execution checks:** preparation counts, time boundaries, target exclusion, input/target alignment, fitted scaling and convergence checks are run on the actual prepared training/validation data.
3. **Predictive validation:** MAE/RMSE compare forecasts with subsequent sensor-reported headcounts. Validation scores are used to select SVR settings, so they are not independent final-test performance estimates.

## Declared modelling choices

| Choice | Implementation |
|---|---|
| Forecast task | Space `227f1068`, 30 minutes ahead, existing prepared splits |
| Input information | Same five inputs and 11 encoded columns as Notebook 4 |
| Scaling | Every encoded column standardised using training means/variances only |
| Target | Sensor-reported headcount in people; not standardised |
| Kernel | RBF |
| Candidate values | `C = [0.1, 1, 10]`; `epsilon = [0.1, 0.5]`; `gamma = [0.01, 0.1]` |
| Starting candidate | `C=1`, `epsilon=0.1`, `gamma=0.1` |
| Selection | Lowest validation MAE, then RMSE, then candidate ID for exact ties |
| Fitting | Every candidate uses all training examples; no sampling or random split |
| Prediction output | Raw values; no rounding or non-negativity clipping |
| Final testing | Not performed in Notebook 5 |

The grid is a small project-specific experiment, not a claim of globally optimal settings. Standardisation changes feature-distance weighting; scaling weekday flags and retaining the Monday-reference encoding are stated design choices. `epsilon` is in people, not minutes, and is not a prediction-accuracy guarantee.

## What the new tests check

| Check group | Expected behaviour |
|---|---|
| Pipeline construction | Returns unfitted scaling and an RBF estimator with the requested parameters |
| Parameter validation | Rejects non-finite, negative or otherwise unsupported settings; zero epsilon is allowed |
| Fitting requirement | Prediction before fitting raises an error |
| Scaling isolation | Stored means/variances equal training-only statistics; future inputs do not change them |
| Prediction stability | Prediction does not refit support vectors or weights; row order is preserved |
| Input preservation | Fitting does not edit the supplied feature table |
| Fractional output | A constant synthetic fractional target is not silently rounded |
| Known nonlinear relationship | Learns a deliberately simple artificial smooth function to a specified tolerance on withheld points |
| Invalid input handling | Missing columns or non-finite values are rejected rather than silently dropped |
| Local model storage | Saving and reloading a trusted local pipeline preserves predictions |

The synthetic nonlinear example uses interleaved withheld points to check smooth interpolation. It does **not** reproduce the project's temporal forecasting problem or prove its real-world accuracy.

## What passing tests and validation do not establish

These checks do not prove sensor headcount accuracy, correct space-to-room mapping, causal relationships, reliable behaviour during outages, cross-space transfer or HVAC energy/comfort savings. Five-minute-old targets may differ from exact target-time headcounts. Complete-case filtering limits coverage and consecutive forecasts are not independent trials.

The current suite is not an exhaustive audit of all earlier data-preparation logic. A successful fit is not proof against overfitting; the chosen validation score is affected by model selection. Final chronological test evaluation and remaining deliverables belong to subsequent stages.
